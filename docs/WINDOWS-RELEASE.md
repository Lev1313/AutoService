# Выпуск AutoService для Windows

Версия 0.5.0, первый показ механику. Windows x64; сборка на Windows 11, Python 3.13.1.
Целевая нижняя граница установщика: Windows 10 1809 x64. На отдельном чистом
компьютере и на каждой версии Windows проверки ещё не было.

## Повторная сборка разработчиком

1. Восстановить `.venv` на 64-разрядном Python 3.13 и установить `requirements.txt`,
   затем `requirements-build.txt`. Для установленного окружения повтор не нужен.
2. Использовать официальный Inno Setup 7.1.1, проверить подпись его установщика
   (Pyrsys B.V., статус Valid). На компьютере разработки компилятор подготовлен
   в отдельной папке временных инструментов; не включать его в пользовательский пакет.
3. Из корня проекта запустить:

```powershell
.\.venv\Scripts\python.exe tools/build_windows.py --output artifacts/release-NEW --compiler "ПОЛНЫЙ ПУТЬ К ISCC.exe"
```

Каталог выпуска должен быть новым. Скрипт не удаляет существующий выпуск.
Он создаёт папку dist/AutoService, русский Setup.exe, portable.zip, SHA256SUMS.txt.
В составе папки — встроенный Python, Qt, ReportLab, инструкция и лицензии.
PATH сборочного процесса очищается от внешних инструментов: обнаруженный при первом
пробном запуске конфликт ICU с Poppler исправлен. Если чужая ICU снова попала в
корень библиотек, скрипт прекращает выпуск до создания установщика.
Не требуется установленный Python на компьютере владельца. Отдельная папка библиотек
сохраняет возможность их замены; не превращать выпуск в один самораспаковывающийся EXE.
Манифест manifest-sha256.json описывает состав папки, кроме самого манифеста.

Исходники, `.venv`, тесты, реальные базы и TXT в дистрибутив не копируются.
Исходный код модулей упакован PyInstaller; отсутствие рядом папки app само по себе
не является проверкой чистого компьютера. Для подтверждения автономности запускать
EXE с очищенными PYTHONHOME/PYTHONPATH/QT_PLUGIN_PATH и ограниченным PATH; проверить
загруженные модули процесса и отсутствие путей к Python/проекту.

## Проверка собранного EXE

Разработчик запускает EXE как отдельные процессы с ограничением времени:

```powershell
AutoService.exe --self-test "НОВЫЙ ОТДЕЛЬНЫЙ КАТАЛОГ"
AutoService.exe --self-test-reopen "ТОТ ЖЕ КАТАЛОГ"
```

Это служебные параметры; в обычном интерфейсе их нет. Сценарий создаёт только
вымышленные данные в явно выделенном новом каталоге, не открывает рабочую базу.
Первый запуск: обновление v2→v6 с копией, машина/контакт/ремонт, правило ТО и перенос
звонка, простой/подробный PDF, CP1251 TXT и защита повтора, backup/restore включая архив.
Второй процесс: сохранность после выхода, проверка схемы/целостности, разделы/поиск,
QtPdf рендеринг, печать в PDF, снимки настоящих окон Windows. Оба кода выхода — 0,
release-check.json: stage=passed, frozen=true. Существующий каталог для первого
сценария отвергается без записи; второй требует специального маркера отчёта.

Дополнительно проверить обычный запуск через ярлык, защиту от второго экземпляра,
повторную установку поверх той же папки и удаление программы. Данные в
%LOCALAPPDATA%/AutoService должны сохраняться; установщик их не содержит и не удаляет.
Тест установки выполняется с отдельной тестовой LOCALAPPDATA и папкой программы,
без доступа к пользовательской базе. Не запускать тестовый uninstaller на рабочей установке.
Готовый сценарий: `tools/verify_windows.ps1 -ReleaseDirectory КАТАЛОГ_ВЫПУСКА
-TestDirectory НОВЫЙ_ТЕСТОВЫЙ_КАТАЛОГ`. Он откажется проводить установку при уже
существующей установке AutoService. Проверяет также блокировку второго процесса,
пути загруженных Python/Qt DLL и неизменность базы вокруг операций установщика.
Обычный запуск приложения может менять служебные счётчики SQLite; хеш сравнивается
непосредственно до/после каждой операции установщика, отдельно от запусков приложения.

## Что остаётся для пилота

Сверить реальные TXT и бланк, когда они появятся; проверить удобство работы владельца.
Значения ТО/реквизиты владелец вводит сам. Одна страница функции печати на HP по USB
подтверждена пользователем; подробности и пределы проверки — RELEASE-0.2.0.md.
Дистрибутив не подписан сертификатом; отдельной проверки SmartScreen на чистой
машине нет. Защиту Windows не отключать. Эти ограничения не считать пройденными.

Основания выбора инструментов: [PyInstaller](https://pyinstaller.org/en/stable/operating-mode.html),
[Inno Setup: установка без прав администратора](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm),
[проверка загрузки Inno](https://jrsoftware.org/isdl-verify.php).


## Изолированная проверка при существующей установке
verify_windows.ps1 по умолчанию останавливает установочный тест, если AppId владельца
уже зарегистрирован. Не удалять его установку ради проверки. Допустим отдельный
проверочный Setup из того же packaging/autoservice.iss и payload с другим AppId.
Для него передать -TestInstaller и -TestApplicationId; GUID обязан отличаться от
основного. /NOICONS /TASKS="" и отдельный /DIR исключают изменение ярлыков/файлов владельца.
Сценарий проверяет сохранение регистрации основной установки до/после. Отдельный
проверочный Setup не выдавать владельцу; выдаётся обычный production Setup с прежним AppId.
Финальная проверка 0.4.0: RELEASE-0.4.0.md.
