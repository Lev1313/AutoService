# Функциональное ТЗ — общие требования (черновик)

## Контекст
Небольшой автосервис: владелец и несколько механиков, но программа — **только для владельца на одном компьютере**. История ремонтов много лет ведётся в отдельных текстовых файлах (и, возможно, бумажных записях). Финансы не ведутся в единой компьютерной системе со слов пользователя. Это не означает отсутствия официальной бухгалтерии.

## Приоритет задач
1. **Напоминать владельцу, когда звонить клиентам и приглашать на ТО** с учётом даты и пробега.
2. **Хранить клиентов, автомобили и историю ремонтных работ** с быстрым поиском.
3. **Печатать квитанции/заказ-наряды** без сложного ввода.
4. **Импортировать существующие TXT-файлы**, не обнуляя многолетнюю историю.
5. Дополнительно: простая запись клиентов на ремонт.

## Принципы UX — обязательные требования
- Осваивается без длительного обучения; ориентир — 10–15 минут знакомства для основных действий (цель, не гарантия).
- Не навязывать механикам статусы «диагностика/ожидание/согласование» или отдельные журналы.
- Никаких обязательных длинных анкет; поля заполняются по мере необходимости.
- Поиск клиента/автомобиля доступен с главного экрана.
- Работа сохраняется без неожиданных потерь; подтверждение перед опасными операциями.
- Свободный текст ремонта — полноценный сценарий, а не запасной.
- Расчёты пробега и напоминаний автоматические, но объяснимые, с возможностью поправить дату вручную.
- Не смешивать «выполнено», «рекомендовано», «оплачено» — данные не додумывать.
- Старые записи можно открыть в оригинальном виде.

## Навигация (предложение)
**Главная / Клиенты / Календарь / Документы**. Ремонты открываются внутри автомобиля; импорт/резервные копии — в Настройках. Прочие разделы по мере реальной необходимости.

## Границы MVP
- Windows, один пользователь, работа офлайн, один локальный файл базы данных.
- Не требуется сервер, сайт, телефонное приложение и постоянный интернет.
- Нет обязательных ролей пользователей, распределения работ между механиками, склада, бухгалтерии, налогового учёта, онлайн-рассылок.
- При этом внутреннюю модель данных проектировать с возможностью расширения.

## Минимальные пользовательские сценарии
1. Позвонил клиент → поиск по телефону/госномеру → открыл историю → назначил звонок/запись.
2. Приехала машина → открыл или добавил автомобиль → ввёл дату, пробег, свободный текст и сумму → сохранил/завершил.
3. После ТО → подтвердил тип выполненного обслуживания (одним простым действием при необходимости) → программа рассчитала будущую дату звонка.
4. Открыл программу утром → видит, кому нужно позвонить; отметил результат и, при необходимости, перенёс.
5. Нужно выдать документ → создал/распечатал квитанцию из имеющихся данных с минимальными дополнительными полями.
6. Первое внедрение → импортировал папку TXT после просмотра результатов, без изменения исходников.

## Нефункциональные требования
- Данные клиента хранятся локально; доступ к компьютеру должен быть защищён.
- Регулярные резервные копии на **другой носитель**; восстановление проверяется.
- Работа с русскими именами, телефонами, госномерами, кодировками и датами.
- Нормальная работа на обычном ПК, без GPU и облачных API.
- Долговременная сопровождаемость; экспорт данных в общедоступный формат.

## Неопределённости
Форма документов, учёт согласия на приглашения, точный объём текущей базы, сроки обслуживания по типам услуг, схема печати, необходимость записи на ремонт. Решения ниже — предварительные, пока владелец не подтвердил.
