# Backlog — идеи, которые НЕ выкидываем

**Принцип:** «Отложено» не значит «никогда». Хранить гипотезу, ценность и причину переноса; возвращаться к ней после наблюдения за работой владельца.

## Небольшие улучшения (после базового MVP)
| Идея | Ценность | Почему не сейчас |
|---|---|---|
| Расписание записи клиентов на ремонт по дням/часам | Планирование загрузки | Основная потребность календаря — звонки на ТО; надо уточнить реальный процесс |
| Колонки по подъёмникам/постам, назначение механика | Планирование нескольких параллельных ремонтов | Владелец один пользуется программой, не хотим заставлять назначать ответственных |
| Гибкие результаты звонков («записался», «отказался», «ТО в другом месте») | История коммуникаций и аналитика | Начать с 2–3 быстрых действий |
| Фото неисправностей и ремонта | История и доказательства состояния | Увеличит сложность ввода и хранения |
| Прикрепление внешних файлов, счетов, фотографий | Полная история авто | Нужна проверка реальной потребности |
| Шаблоны типовых работ и цен | Ускорение квитанций | Нельзя навязывать справочники вместо свободного текста |
| Подробные позиции работ/деталей, скидки | Детализированная квитанция | Может оказаться обязательным — выяснить по образцам документов |
| Напоминания по рекомендациям («проверить подвеску») | Возврат клиента на отложенную работу | Отличать от регламентного ТО, не перегружать список |
| Слияние дубликатов клиентов/авто | Чистая база | Нужен безопасный UI и настоящие случаи |
| Импорт/экспорт Excel, CSV | Миграция/отчёты | TXT-импорт важнее; экспорт как страховка полезен |
| Поиск по любым словам из текста ремонтов | Быстро найти старую неисправность | Полезно после наполнения базы |
| Дополнительный выбор темы, тёмный режим | Комфорт | После проверки основного сценария |

## Более крупные функциональные модули
| Идея | Ценность | Почему отложена |
|---|---|---|
| Полноценный склад запчастей, остатки и списания | Контроль остатков | Сложнее, чем текущий учёт, неизвестна потребность |
| Закупки, поставщики, закупочные цены | Себестоимость работ | Потребует дисциплины ввода и отдельной логики |
| Управленческие финансы (выручка/расходы/прибыль) | Видимость результатов бизнеса | Владелец пока просил другие вещи; бухгалтерией не подменять |
| Зарплаты и учёт трудозатрат сотрудников | Управление командой | Не навязывать механикам тайм-трекинг |
| Аналитика выручки, повторных визитов, результативности звонков | Обратная связь | Сначала нужны достоверные данные |
| Гарантии на работы и запчасти, гарантийные обращения | Контроль обязательств | Требует продуманного правового/процессного оформления |
| Согласование дополнительных работ и стоимости | Контроль процесса ремонта | Нельзя предполагать текущий процесс без механика |
| Подробные этапные статусы ремонта | Производственное планирование | **Специально отвергнуто для стартового UX** |
| Раздельная закупочная/розничная стоимость и источник детали | Маржинальность и качество документов | Нельзя превращать каждую заметку в учётную таблицу |

## Интеграции и автоматизация
- Отправка SMS, Telegram, WhatsApp/мессенджеров по разрешённым каналам — зависит от согласия, API, стоимости, требований к персональным данным.
- Автоматический телефонный обзвон — совсем не обязательно, владелец хотел напоминать **себе**, когда позвонить.
- Интеграция с ККТ, эквайрингом, 1С и бухгалтерией — только при наличии бизнес-потребности, отдельные требования.
- VIN-декодер и каталоги запчастей, внешние сервисы истории авто — требуют доступа к данным и возможно подписки.
- Интеграция с OBD/диагностическим оборудованием — дополнительный крупный проект.
- Автоматическое извлечение структуры ремонта ИИ, классификация работ из свободного текста — нельзя незаметно считать вывод модели фактом.
- Резервное копирование/синхронизация через облако — сейчас офлайн, нет необходимости в платном сервере.

## Архитектурное масштабирование
- Сетевой доступ с нескольких ПК через локальную сеть; при необходимости — сервис/сервер в помещении.
- Мобильный/браузерный интерфейс, роли владельца и механиков, многопользовательская работа.
- Система для нескольких филиалов; затем коммерческий SaaS для других небольших СТО.
- Продажа/лицензирование продукта — пользователь упомянул разработку бесплатно знакомому механику, коммерциализация обсуждалась лишь как возможность. Важно заранее согласовать права на код и данные.

## Риски, о которых нельзя забывать даже при простом MVP
Автоматические бэкапы и восстановление, сохранность первичных файлов, защита персональных данных, юридическая корректность документов. Это **не backlog на потом** — базовую защиту надо предусмотреть сразу.
